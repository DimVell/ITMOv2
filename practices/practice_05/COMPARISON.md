# Kiro и OpenSpec: применение и сравнение

## Что применено

В Kiro-формате создан steering (`product.md`, `tech.md`, `structure.md`) и две feature-spec:
каждая состоит из `requirements.md`, `design.md`, `tasks.md`. Независимые черновики команд
сначала сохранены отдельно; расхождения по статусам, JSON, дубликатам и валидации разрешены в
общем контракте, после чего обновлены обе Kiro-спеки и только затем реализован код.

OpenSpec в репозитории уже инициализирован (`openspec/config.yaml`, команды `opsx-*`), поэтому
сравнение опирается на реально доступную структуру, но ДЗ выполнено не через него.

## Сравнение на этой фиче

| Аспект | Kiro | OpenSpec | Наблюдение |
|---|---|---|---|
| Постоянный контекст | `.kiro/steering/*` | `openspec/config.yaml`, main specs | Kiro явно разделяет product/tech/structure |
| Фича | requirements → design → tasks | proposal → specs/design → tasks | Обе модели делают намерение видимым до кода |
| Изменение требований | правка документов feature | update change + delta specs | OpenSpec лучше подчёркивает дельту и lifecycle |
| Завершение | checked tasks, история Git | sync + archive | OpenSpec даёт более явный архив завершённых changes |
| Две команды | две соседние feature-spec + contract | два change или общий change с несколькими specs | В Kiro было проще показать два независимых черновика |
| Tooling | встроено в Kiro IDE | отдельный CLI и разные coding clients | Kiro связан с IDE; OpenSpec переносимее |

## Вывод

Для небольшой учебной фичи Kiro оказался прямолинейнее: три понятных документа на команду и
steering без отдельного archive-цикла. Цена — договорённости «до/после» и общий контракт
пришлось оформить явно, потому что Git/Kiro сами не навязывают change lifecycle. OpenSpec
лучше подходит, когда важны delta-specs, строгая CLI-валидация и архив изменений; для этой
задачи такой процесс дал бы больше церемонии без изменения контракта или тестов.
